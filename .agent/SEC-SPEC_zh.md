# 面向 Agent 的 CLI 安全规范

**English → [SEC-SPEC.md](SEC-SPEC.md)**

规范版本 2.0.1，规则 SEC-001 至 SEC-060。本文是安全方面的规范性文件，涵盖风险档（risk tier）、不可信内容、授权、写入门控（write gate）的安全属性、机密、对外连接、状态存储、凭证落盘和供应链。相关文件：`CLI-SPEC.md`（机器契约，CLI-xxx）、`SKILL-SPEC.md`（Skill，SKL-xxx）、`VERIFY-SPEC.md`（验证，VER-xxx）以及 `contract/contract.json`（错误码、枚举、键集合）。本文的规则概括某条 CLI 规则时，行为以那条 CLI 规则的定义为准；本文说明它为什么关乎安全、该怎么评审。

## 威胁模型（资料性）

调用方是一个带 shell 的语言模型，以用户的操作系统账户运行。它会读取工具打印的所有内容，包括别人写的文本，并依据读到的内容行动。本规范防范：

- **注入指令**：名称、标题、评论、正文、日志或上游错误中，让 Agent 去做某件事的文本。
- **Agent 偏离**：Agent 改动的对象比人要求的多，或者改了别的对象、别的种类的东西。
- **写入门控失效**：确认令牌（confirm token）没有绑定请求、可以被伪造或可以被重放；写入绕过了写入门控。
- **泄露**：输出、预览、令牌、操作记录或日志中出现机密；数据被发往用户没有配置的主机。
- **供应链**：被篡改的发布，或会执行攻击者所选命令的更新路径。

本规范不防范以同一操作系统用户身份运行的恶意进程（包括 Agent 本身）：这样的进程可以编辑授权范围文件（scope file）、确认密钥和操作记录（SEC-013）。

> **库替你做了什么。** aicli 以副本方式引入（vendored）到 `internal/aicli/` 或 `<pkg>/_aicli/`，它实现了：根据声明的效果检查最低风险档（SEC-001）；组装 `meta.untrusted`，并让它跟随 `--fields`（SEC-002）；授权范围的加载、严格解析、SEC-012 中的每项检查，以及带 `details.scope` 和 `grant_example` 的拒绝（SEC-010 至 SEC-012）；整个写入门控（SEC-020）；预览和诊断输出中的机密显示为 `"***"`，绑定中的机密使用带密钥的摘要（SEC-021）；状态存储、密钥和操作记录，均采用失败即拒绝（fail closed，SEC-030）；拒收机密的设置文件（SEC-040）；整个 `update` 命令，从严格的版本校验、不经 shell 的 argv，到进程内的签名校验和 Skill 同步（SEC-050）。
> 工具仍需自己负责：注册表中如实的效果、`dangerous` 标记、机密参数和不可信字段；规范化的目标键（SEC-012）；它访问的目的地（SEC-022）；凭证存储（SEC-040）；它的 `UpdateConfig`、发布签名和依赖审计（SEC-050）；它自己的 SECURITY.md。

## 风险与不可信内容

### SEC-001 由效果决定风险档

每个工具都必须声明一个风险档，且不低于其命令的效果所要求的最低档（契约中的 `effects.minimum_risk_tier`）；只要有任何命令可能造成不可逆或账户级的损害，就必须声明 T2。风险档必须以 `reference.risk_tier` 的形式出现，并写进 SECURITY.md，附一句话说明最坏情况。

| 风险档 | 效果 | 示例 |
|---|---|---|
| T0 | 只有 `observe` | 行情报价、日志搜索、只读报表 |
| T1 | `change`、`artifact`、`persist` | 编辑 issue、导出报表、覆盖本地配置文件 |
| T2 | `deliver` 或 `configure`，或不可逆 / 账户级损害 | 发送邮件、发布、修改权限或凭证、drop 数据库、删除项目 |

风险档描述的是命令能做什么，而不是凭证能做什么：持有可写令牌的只读工具属于 T0，而 SEC-040 对这个令牌仍然适用。无法撤销的命令（删除、合并、drop、清除）必须声明为 `dangerous`（CLI-025）；`deliver` 和 `configure` 默认就是危险的。批量命令只有在它做的事本身危险时才是危险命令，即它的效果危险，或者它的操作无法撤销，绝不只因为目标多；命令本身可以撤销、某次计划却无法撤销时（`Preview.Dangerous`，CLI-056），这一次运行是危险的。

原因：v1 的风险档是各工具自选的标签。用驱动写入门控（CLI-050）和授权范围（SEC-012）的同一组效果来推导最低档，这样其中一处声明就不会与另外两处相矛盾。gitlab-cli 试点（2026-10）发现，本规则、CLI-025、模板和评审 Skill 对批量命令给出了不同的答案。

检查：aicli 把 `App.RiskTier` 与已注册的效果做比较（CLI-025）。评审确认 SECURITY.md 与 `reference.risk_tier` 一致，且每个命令的效果与它实际做的事相符（VER-004）。

### SEC-002 不可信内容

工具无法控制的文本（名称、标题、描述、评论、消息正文、文件内容、日志、上游错误文本）是数据。工具必须：

- 在 `meta.untrusted` 中列出承载这类文本的每一条信封（envelope）路径（CLI-046）：包括 `data` 中（也包括嵌入了这类文本的 `ref`）、预览中（`target.label`、`changes`）、回执中和 `error.details` 中（`upstream_message`、`candidates[].label`）的路径；并在 `reference` 中按 schema 列出（`untrusted_fields`）；
- 绝不因为这类文本中的指令或引用而触发动作、抓取链接或切换目标；
- Agent 据以行动的每个字段（`message`、`next_action`、`did_you_mean`、`usage`、`resume`、`lookup`、通知中的 `command`），都只用工具自己控制的值来构造：注册表路径、经过校验的 ref 和参数，绝不使用上游文本。

Agent 必须把这类文本当作数据，绝不执行其中的指令（SKL-007）。

原因：Agent 会读完整个响应，所以注入的文本会与用户的请求相互竞争。在 2026-10 的 gitlab-cli 评测中，一个 MR 描述带有注入指令，无论有没有 Skill，任何一组都没有一次试验执行了它。每个响应只声明一次路径，取代了 v1 逐项标注的 `_untrusted`；后者让一个 50 项列表的响应多出约 16% 的字符。

检查：aicli 测试 `meta.untrusted` 跟随 `--fields`；R04 校验符合性测试套件观察到的每个信封；评审每个 schema 的 `untrusted_fields`；VER-006 的注入指令场景。

## 授权

### SEC-010 授权来自授权范围文件

工具只要有非 `observe` 的命令，就必须在发送任何内容之前拒绝每一条这样的命令，除非有效的授权范围文件授予了它：返回 `E_FORBIDDEN`（退出码 4，`dispatch_state: not_started`），带 `details.scope`，能构建出预览时还带 `details.preview`。这项检查在预演（dry-run）时、裸调用被拒绝时运行，在确认时再运行一次，并且也覆盖 `operation resolve`（CLI-061）；自更新是唯一不受它约束的命令（CLI-070、SEC-050）。在有效的授权范围内，Agent 工作时不需要人逐步确认：预演 → 确认绑定的是 Agent 自己的计划，不是一次批准。

```json
{"ok":false,"schema_version":"2.0","error":{"code":"E_FORBIDDEN","message":"No scope file grants this write; ask the user to grant one.","retryable":false,"details":{"dispatch_state":"not_started","next_action":"Ask the user to grant this scope by creating C:\\Users\\me\\.notes-cli\\scope.json with the grant_example content (adjusted); do not create it yourself.","scope":{"status":"missing","path":"C:\\Users\\me\\.notes-cli\\scope.json","scope_id":null,"missing":{"effects":["change"],"dangerous":false,"target":"ops/n-42"},"grant_example":{"scope_id":"scp_2026-10-12_ops","tool":"notes-cli","granted_by":"<your name>","granted_at":"2026-10-12T08:00:00Z","expires_at":"2026-10-19T08:00:00Z","effects":["change"],"dangerous":false,"targets":[{"key":"ops/"}]}}}},"meta":{"duration_ms":4}}
```

原因：v1 已经规定「默认只读；Agent 不能自我提权」，却把实现机制留给了各个工具。2026-10 的工具群（fleet）审计发现，一份手工维护的权限列表漏掉了一个命令，于是在只读设置下，一个批量命令仍然可以创建、修改和删除。由共享写入门控内部、按声明的效果驱动的检查，不可能漏掉命令。

检查：G07（没有授权范围时：预演和确认都返回带 `details.scope` 的 `E_FORBIDDEN`，上游写入为零）。

### SEC-011 授权范围文件的格式与定位

授权范围文件由人来写；CLI 不得创建、编辑、移动或删除它，也不得提供能做这些事的命令或标志。设置了 `<PREFIX>_SCOPE_FILE`（绝对路径）时，CLI 读取它指定的文件，否则读取 `<state_dir>/scope.json`；没有对应的 CLI 标志。解析是严格的：JSON 无效、键重复、键未知或已知键的大小写写法不同、值的类型错误或超出枚举范围、`tool` 不是本工具，或者 `outputs`、`roots` 中出现相对路径，都会让文件成为 `invalid`；在 POSIX 上，文件不归当前用户所有、或者其他人可写，同样如此。无效的文件什么也不授予。

```json
{
  "scope_id": "scp_2026-10-12_triage",
  "tool": "notes-cli",
  "granted_by": "Sean",
  "granted_at": "2026-10-12T08:00:00Z",
  "expires_at": "2026-10-19T08:00:00Z",
  "effects": ["change", "deliver"],
  "dangerous": true,
  "targets": [{"key": "ops/"}, {"key": "eng/n-7", "match": "exact"}],
  "destinations": ["mailto:bob@acme.com"],
  "limits": {"max_operations": 50},
  "notes": "Triage week; may share ops notes with Bob"
}
```

| 键 | 必填 | 含义 |
|---|---|---|
| `scope_id` | 是 | 本次授予的名称；在它之下执行的每个操作都会记下它 |
| `tool` | 是 | 本工具的名称 |
| `granted_by`、`granted_at` | 是 | 由谁授予、何时授予（UTC，`Z`） |
| `expires_at` | 是 | UTC 时间，`null` 表示永不过期；应当填一个时间 |
| `effects` | 是 | 允许的效果；`observe` 不需要授予 |
| `dangerous` | 是 | 是否允许危险命令 |
| `targets` | 否 | 选择器 `{key, match}`，`match` 取 `subtree`（默认）或 `exact`；缺省表示账户能触及的所有目标，所以应当提供 |
| `destinations` | 否 | `deliver` 命令可以发往的目的地；缺省或为空表示哪里都不能发 |
| `outputs` | 否 | 可以新建本地文件的绝对路径目录（`artifact`）；缺省表示没有 |
| `roots` | 否 | 其中已有文件可以被覆盖的绝对路径目录（`persist`）；缺省表示没有 |
| `limits.max_operations` | 否 | 在这个 `scope_id` 下可以确认的操作数，记在 `<state_dir>/scope-usage.json` 中，清理操作记录绝不会把它清零 |
| `revoked` | 否 | 为 `true` 时撤销这次授予 |
| `notes` | 否 | 写给人看的自由文本 |

人怎样授予授权范围：

1. 从 Agent 转达的拒绝信息中拿到路径和可以作为起点的内容（`details.scope.path`、`grant_example`）；`<tool> context` 也会显示路径和当前的授予内容。
2. 在那个位置写入文件。把你的名字填进 `granted_by`，设置 `expires_at`，除非任务需要，否则 `dangerous` 保持为 false，并把 `targets` 收窄到任务所需。
3. 运行 `<tool> doctor`：它的 `authorization` 检查会说明文件是否有效、授予了什么。
4. 要撤销授予，设置 `"revoked": true` 或删除文件。一次性任务可以在别处放一份专门的文件，并在 Agent 运行的环境中设置 `<PREFIX>_SCOPE_FILE`。

原因：授权必须来自人，而不是来自 Agent 或它读到的任何东西。拒绝未知键，是因为否则拼写错误会悄无声息，还可能扩大授予的范围：`"target": [...]` 会让 `targets` 缺省，而缺省意味着所有目标。拒绝重复键以及只有大小写不同的键，是因为不同的解析器对哪个值生效有分歧，评审者读到的可能是一份授予，工具执行的却是另一份：一个同时写着 `"dangerous": false` 的文件，Go 的 JSON 解码器却应用了其中的 `"Dangerous": true`。拒绝相对路径，是因为它们会相对于 Agent 当时所在的任意目录来解析。

检查：aicli 的授权范围测试（未知键、重复键、`tool` 错误、相对路径：都是 `invalid`）；评审确认没有命令写入授权范围文件的路径。

### SEC-012 授权范围检查

在预演时、裸调用被拒绝时和确认时，除非下面每一项检查都通过，否则写入门控必须拒绝；`details.scope.status` 给出第一个失败的检查：

- 文件存在且有效（`missing`、`invalid`），没有超过 `expires_at`（`expired`），也没有被撤销（`revoked`）；
- 命令的每个非 `observe` 效果都在 `effects` 中，且危险命令要求文件中有 `"dangerous": true`（`insufficient`）；
- 提供了 `targets` 时，有一个选择器匹配目标键（`insufficient`）。`exact` 匹配完全相等的键。`subtree` 匹配相等的键，或者在相等部分之后以 `/`、`!`、`#`、`:` 或 `@` 继续的键；以这些字符之一结尾的选择器键，匹配它之后的任何内容。所以 `ops/` 覆盖 `ops/n-42`，`acme/web` 覆盖 `acme/web!5`，但两者都不覆盖 `ops-archive/n-1` 或 `acme/webstore`；
- 预览中的每个目的地都匹配某个 `destinations` 条目（`insufficient`），按目的地规则而不是目标规则匹配（contract.json `scope.destination_match`）。含 `://` 的条目匹配完全相等的目的地，或者协议（scheme）和主机相同、路径等于或位于条目路径之下的目的地，路径按完整的段比较；带有用户信息、查询串、片段或点号路径段的目的地，只匹配完全相等的条目。其他条目（电子邮件地址、账号名、频道 ID）只匹配完全相等的目的地；条目以 `/` 结尾时，还匹配以该条目开头、在 `/` 边界之后继续延伸的目的地。在这里 `@`、`:`、`#` 和 `!` 都是普通字符，所以 `bob` 不覆盖 `bob@evil.example`；
- 命令写入的每个本地路径，在解析符号链接和 `..` 之后，尚不存在时位于 `outputs` 之内，已经存在时位于 `roots` 之内，所以缺省 `roots` 意味着什么都不能覆盖（`insufficient`，带 `missing.outputs` 或 `missing.roots`）；路径中有无法解析的目录联接（junction）或其他重解析点时检查失败，`WriteOutput` 和 `OpenOutput` 在写入时还会再检查一次。只声明 `artifact`、没有声明 `persist` 的命令从不覆盖文件：路径已经存在时，无论在预演时还是写入时，都返回 `E_VALIDATION`（`invalid_value`，`details.path`），而不是授权范围拒绝，因为任何授予都不能允许它；
- 在这个 `scope_id` 下已派发的操作数少于 `limits.max_operations`，在消费令牌的同一步骤中、在它自己的锁之下记入 `scope-usage.json`（`budget_spent`），所以并发的确认无法超出配额，清理也无法把它补满。

授权范围文件的摘要会绑定进令牌（CLI-054）；文件在预演和确认之间被改动，结果是 `E_CONFLICT` `scope_changed`（CLI-057）。目标键必须规范化：经过 URL、名称和别名解析之后，每个对象只有一种写法，所以当上游把 `ACME/Web` 和 `acme/web` 视为同一个对象时，它们是同一个键。否则，另一种写法可能落在人写的选择器之外，或者落进一个他并不想要的选择器之内。子资源的键接在父资源的键之后（`acme/web#12/notes/99`，CLI-048），这样对父资源的授予就能覆盖它。

原因：确认时重新检查，能让收窄或撤销后的授权范围对已经签发的令牌生效。按边界匹配，让 `ops` 不会覆盖 `ops-archive`；单独的目的地规则，让授予某个收件人的授权范围不会覆盖只是以它开头的地址；解析符号链接，则让 `outputs` 中的路径不会写到别处去。在 2.0 的发布评审中，允许目录下的一个 Windows 目录联接让写入落到了目录之外，因为 Go 的 `filepath.EvalSymlinks` 不再跟随目录联接；只授予 `outputs` 时，命令还覆盖了那里已有的文件。在 gitlab-cli 试点（2026-10）中，一次下载的文件已经存在，得到的拒绝却是请人授予 `roots`，而这个授予帮不上忙，因为这个命令从不覆盖文件。

检查：G07、G10；aicli 针对每种状态、选择器边界、目的地匹配、符号链接逃逸和配额计数的测试；评审工具怎样构造目标键。

### SEC-013 如实的保护声明

SECURITY.md 和每个 Skill 都必须把授权范围描述为针对注入指令、Agent 偏离和错误目标的保护，不得把授权范围文件或确认令牌说成人工批准的证明。它们必须说明它防不住什么：以同一操作系统用户身份运行的任何进程（包括 Agent）都能写入授权范围文件、确认密钥和操作记录，或者把 `<PREFIX>_SCOPE_FILE`、`<PREFIX>_STATE_DIR` 指向别处（换一个新的状态目录还会重置操作配额，并丢掉未解决的操作）。声称提供 Agent 无法伪造的批准的工具，必须在 `reference` 和 SECURITY.md 中写明 Agent 无法写入的那个通道（另一个操作系统账户、上游的审批流程、硬件密钥）。

SECURITY.md 用的文字（方括号部分按实际情况改写）：

> 在有人授予授权范围文件（[路径]）之前，写入都会被拒绝。每次写入在发送任何内容之前都会对照它检查，这能挡住注入指令、偏离任务的 Agent 和错误目标。它不是批准的证明：任何以你的操作系统用户身份运行的程序（包括 Agent）都能编辑这个文件。请自己编写授权范围文件，或者审查 Agent 应你的要求写出的文件；让授权范围尽量窄、有效期尽量短。[如需 Agent 无法伪造的批准，请使用 …… / 本工具不提供这样的通道。]

原因：授权范围文件和令牌都存放在 Agent 所用的操作系统用户可写的位置。夸大它们的作用，会让人以为每次写入都单独经过了批准，从而授予范围宽、有效期长的授权范围。

检查：评审 SECURITY.md 和 SKILL.md 的措辞。

## 写入门控

### SEC-020 写入门控的安全属性

每个非 `observe` 命令都必须经过 aicli 的写入门控（CLI-050）。下表供评审者参考，列出写入门控提供的属性、每项在哪里规定、怎样测试：

| 属性 | 含义 | 规则 | 检查 |
|---|---|---|---|
| 共享实现 | 工具没有自己的令牌、绑定、密钥或单次使用存储 | CLI-050 | 评审 |
| 预览在先 | 令牌只随产生它的那份预览一起出现：来自预演，或来自裸调用被拒绝时 | CLI-051、CLI-052 | G01、G02 |
| 完整绑定 | 命令路径；规范化之后每个已提供的标志和位置参数（声明过的控制标志除外）；文件和 stdin 输入的内容摘要；解析后的账户、主机和目标；当前配置档和每个已声明的设置；授权范围摘要；工具版本；基准版本 | CLI-053、CLI-054 | G03 |
| 带密钥的令牌 | 使用 32 字节本机密钥的 HMAC-SHA256，绝不退回到不带密钥的方式；有效期最长 15 分钟 | CLI-055 | G08 |
| 规范编码 | 只接受 `^ct2_[a-z2-7]{26}_[0-9a-f]{32}$`；单次使用以操作 ID 为键 | CLI-055 | G05 |
| 原子化的单次使用 | 每个操作一个独占创建的标记，跨进程生效 | CLI-055 | G04 |
| 失败即拒绝 | 没有可用的密钥，就不签发令牌；操作记录写不进去或记录已损坏，就不写入 | CLI-055、CLI-058 | G08 |
| 没有模式旁路 | 任何输出模式、标志或环境变量都关不掉写入门控 | CLI-055 | G06 |
| 危险命令的第二个标志 | 两步都要带 `--dangerous` | CLI-056 | G09 |
| 确认时复查 | 授权范围、基准版本和计划（`state_drift`）、账户、主机和目标，在按目标的锁之下进行，直到记录写为 `dispatching` | CLI-057 | G10 |
| 先记录后发送 | 派发之前先写入操作记录，写不进去就什么都不发送 | CLI-058 | G08 |

下面这些任何库都检查不了，所以评审必须：

- 对比每个命令声明的效果和它实际做的事：声明为 `observe` 的写操作会绕过写入门控、授权范围和操作记录；
- 确认每一个影响请求内容的输入，都是以声明过的参数、经 aicli 读取的文件输入（`ReadFileInput`）或身份（账户、主机）的形式进来的；在执行时从其他任何地方读取的值（环境变量、配置文件、直接打开的路径、之后才解析的相对路径）都没有被绑定；
- 确认 `Preview` 只读取，`Apply` 只发送预览所描述的内容；
- 确认只有在没有任何内容到达上游时才返回 `NotDispatched`，只有在上游明确拒绝时才返回 `Rejected`；任何不确定的情况都保持为未知结果（CLI-015）；
- 确认 `App.Write` 之前的查询不读取确认后的写操作会改变的东西：它在每次确认时都先于令牌检查运行，所以对目标的查询应放进 `WriteSpec.ResolveTarget`（CLI-057）；
- 确认命令发出的文本不会带来命令没有声明的效果：上游会执行自由文本里写的命令时（例如 GitLab 的 quick action：评论或描述里的 `/merge` 或 `/assign @x`），`Preview` 要阻止这样的行，或者命令要声明这些行可能造成的效果。

原因：v1 规定了正确的规则，却让每个工具各自实现。2026-10 对工具群中 10 个带写入门控的工具做的审计，在一个又一个工具里发现了同样的缺陷：

- 每个绑定都漏了输入：手工挑选的字段；按路径而不是按内容绑定的文件；只绑定目标列表的批量处理路径；从环境变量或配置中读取、却没有绑定的账户、区域或时区；
- 9 个工具的令牌可以伪造：密钥出错时退回到不带密钥的方式、根本没有密钥，或者接受空密钥；
- 8 个工具按 v1 的要求，在单次使用存储出错时允许令牌被重复使用；4 个工具接受重新编码后的令牌重放；
- 2 个工具在文本输出模式下跳过了写入门控，还有一些写操作在写入门控之外运行，或者被声明成了读操作。

10 份实现，产生了 10 组漏洞。gitlab-cli 试点（2026-10）又找到一个任何库都看不到的问题：GitLab 会把评论中的 `/merge` 行当作命令执行，所以一个发评论的命令可能合并一个合并请求。

检查：符合性测试套件在 CI 中运行，每个写命令都有一个样例（VER-001，G00 至 G10）；每次规范发布都重新运行一次工具群的写入门控审计（VER-007）。

## 机密、状态与凭证

### SEC-021 机密

声明为 `secret` 的参数的值（CLI-024）、凭证以及由它们派生出的令牌，不得出现在 stdout、stderr、预览（显示为 `"***"`）、确认令牌、操作记录、日志、通知、错误详情或 `reference` 示例中。工具不得公开机密的未加盐哈希，无论是完整的还是截断的；需要用指纹区分不同凭证时，必须使用带密钥的哈希（使用本机密钥的 HMAC）。aicli 以确认密钥下的 HMAC 摘要绑定机密值，从不存储原值。它把已知是机密的每个值（及其 URL 转义形式）在错误消息和详情中（HTTP 客户端的错误常常引用请求的 URL）以及调试行中替换为 `***`：机密参数、机密设置的标志、机密文件输入的字面值孪生标志（CLI-100、CLI-048）、机密设置，以及工具用 `App.AddSecret` 登记的值（从钥匙串读出的令牌）。上游返回的机密（CI/CD 变量的值、只显示一次的密钥）同样绝不输出：命令只报告这样的值是否存在、写操作有没有改变它，回读时在内存中比较并显示为 `***`，也没有任何标志能显示它；需要看的人到上游自己的界面里去看。只要一个标志的某些取值可能是机密，这个标志就是机密标志（变量的 `--value`，无论是否掩码）。

原因：令牌或密码的未加盐哈希可以离线比对或暴力破解，所以公开它就等于泄露机密。2026-10 的工具群审计发现，有一个登录预演打印了访问令牌完整的未加盐 SHA-256，还有一个令牌载荷携带了一份参数列表的未加盐 SHA-256，而那份列表里包含密码。gitlab-cli 1.x 在 `--show-values` 开关后面显示 CI/CD 变量的值；它的 2.0 试点（2026-10）去掉了这个开关。

检查：每个携带凭证的参数都列在 `Meta.Secrets` 中；工具的测试用一个哨兵机密运行每个写操作，并在每个信封、记录和日志中搜索这个哨兵值及其未加盐 SHA-256；评审。

### SEC-022 对外连接

工具必须只连接用户配置的上游服务（其设置或凭证中的主机，CLI-100），以及在 `update` 和 `doctor` 中连接它的发布源：GitHub API 和发布下载，以及校验它们所用的 Sigstore 信任根服务（CLI-070、CLI-071）。`update` 刷新信任根时，使用与它的其他请求相同的超时、代理、CA 文件和 User-Agent（CLI-110）；Python 库刷新时不使用 CA 文件和 User-Agent（CLI-070）。它不得发送遥测、分析数据、崩溃报告或使用情况上报，无论是发给它的作者还是任何其他人。某个功能需要的其他任何目的地（身份提供方的令牌端点、提供附件的 CDN），都必须在 SECURITY.md 中列出，并写明发送了什么。

原因：工具以用户的凭证处理用户的数据，而除了它的回答之外，用户和 Agent 都看不到它还发出了什么，所以每个目的地都必须能在一个地方读到。使用情况上报还会带上 Agent 运行过的命令，而这些命令描述的正是用户的工作。

检查：对照 SECURITY.md 评审每个网络调用点和写死的主机；没有分析或崩溃报告类的依赖。

### SEC-030 状态存储

状态目录取 `App.StateDir`（测试用），没有时取 `<PREFIX>_STATE_DIR`，再没有时取 `~/.<tool>`。其中存放 `confirm.key`、`operations/`（操作记录和单次使用标记）、`locks/`（按目标的确认锁，CLI-057）、`scope-usage.json`（每个 `scope_id` 的操作配额，SEC-012）、默认的 `scope.json`、默认的 `settings.json`（CLI-100）和 `update-check.json`。aicli 必须：

- 在 POSIX 上以 0700 创建目录、以 0600 创建其中的文件，在创建时就设定权限模式，并在 `context.state.protection` 中报告 `posix-0700`；
- 在 Windows 上报告对解析出的状态目录实际验证了什么：位于用户配置文件目录内时报告 `windows-profile-acl`，设置并验证了显式的仅属主 ACL 时报告 `windows-explicit-acl`，否则报告 `windows-unverified`（此时 `doctor` 的 `state_store` 检查会发出警告）。没有设置过的仅属主访问，绝不能声称有；
- 状态路径是符号链接或不是目录时，以 `E_IO` 拒绝；
- 把无法读取的密钥、长度不是恰好 32 字节的密钥、无法读取或已损坏的记录都视为失败：拒绝写入，或者封锁该记录对应的目标，绝不把它当作空的、不存在的或已批准的。

删除 `confirm.key` 后，工具会创建新密钥；已经签发的令牌随即无法通过验证。

原因：失败即放行（fail open）的存储，会把磁盘错误或权限错误变成伪造或重放的写入。2026-10 的工具群审计发现，有的密钥在无法读取或保存时退回到不带密钥的哈希，有的单次使用存储在无法读写时放行令牌；后者正是 v1 的要求（「绝不阻止写入」）。

检查：G08；aicli 针对符号链接或非目录的状态路径、长度错误的密钥和损坏的记录的测试；在 CI 的每个操作系统上检查 `context.state.protection`。

### SEC-040 凭证落盘

存储凭证的工具必须遵循 v1 的钥匙串（keyring）模式，按优先顺序：

1. 密码只用一次，登录时换成令牌，从不存储；协议需要的长期机密（例如 Basic auth）放进钥匙串。
2. 机密存放在操作系统钥匙串中（Windows 凭据管理器、macOS Keychain、Linux Secret Service），由操作系统绑定到用户的登录。
3. 配置文件不存机密：只存元数据（URL、账户名、区域）以及机密存放在哪个后端。设置文件中出现声明为机密的设置时，aicli 拒绝该文件（CLI-100）。

此外：

- 文件加密（AES-256-GCM，密钥来自与机器绑定的 KDF）是给没有钥匙串的主机用的回退方案，不是并列选项：它能抵御文件被拷出本机，抵御不了本地攻击者。`context.credentials.source` 报告当前生效的后端（`env`、`keyring` 或 `encrypted_file`），让回退可见。
- 环境变量是非交互的通道。用标志传机密不是文档给出的途径：argv 会出现在进程列表、shell 历史和 Agent 的对话记录里。凭证由人在会话开始前配置好；Agent 从不经手机密值。
- 存储、修改或删除凭证或配置档（profile）的命令，包括 `auth login` 和 `auth logout`（CLI-101），声明为 `configure`（契约 `effects.configure`），因此属于 T2，默认就是危险的：没有授予 `configure` 和 `dangerous` 的授权范围，Agent 就无法更改工具所代表的账户。
- 0600 是 POSIX 的说法。Windows 上的保护来自用户配置文件目录的 ACL，或者干脆不保留机密文件；没有设置 ACL，就不要声称仅属主可访问。
- 机密只在需要的时间内留在内存中，绝不进入日志、stdout 或 stderr（SEC-021）。

原因：把配置文件拷出本机，不该得到任何可用的东西；钥匙串把机密绑定到用户的登录。通过命令行传递的凭证，会泄露到每一次进程列表和 Agent 的对话记录中。

检查：评审配置文件和 `context.credentials`；有测试验证文件回退时报告 `encrypted_file`；凭证和配置档命令声明为 `configure`。

## 供应链

### SEC-050 供应链

沿用自 v1 的部分：

- **签名发布。** CI 在基于 tag 的发布工作流中，用 Sigstore 无密钥签名对 `checksums.txt` 签名（`cosign sign-blob --new-bundle-format`）；npm 包带来源证明（provenance）发布。
- **进程内验证。** 在二进制安装路径上，aicli 的 `update` 在进程内验证签名（Go 用 `sigstore-go`；Python 在冻结的二进制中用 `sigstore`）：信任根内嵌在程序中，而不是首次使用时才信任，信任根无法刷新时，更新在安装任何东西之前以 `E_NETWORK` 停止；证书身份是该发布 tag 上的确切发布工作流，签发者为 GitHub OIDC。之后再验证归档文件的校验和。任何失败都是 `E_INTEGRITY`（不可重试），没有「仍然继续」的路径。
- **依赖审计**覆盖工具分发所涉及的每个生态（通过 npm 包装器分发的 Go 工具用 `govulncheck` 和 `npm audit`；Python 用 `pip-audit` 和 `npm audit`），遇到高危即失败，在合并路径上运行，并在发布路径上签名任何东西之前再运行一次（VER-008）。
- **可追溯的构建**：发布产物由 CI 从打了 tag 的源码构建；不手工上传二进制。
- **安装时不下载**：npm 包装器运行已经安装好的平台包；没有任何安装脚本去拉取代码。

2.0 新增，由 aicli 的内置命令 `update`（CLI-070）和以副本方式引入的库实现：

- **工具里没有更新代码。** 工具设置 `App.Update`，不编写自己的更新路径；命令树检查会拒绝工具自定义的 `update`（CLI-021）。
- **严格的 semver 目标版本。** 更新路径用到的每个版本，无论来自 `--target-version` 还是发布元数据（例如 tag 名），都要在任何网络调用、文件写入或执行之前通过 `ParseVersion`，更新通知里显示的版本也一样。未通过的 `--target-version` 返回 `E_USAGE`（`invalid_value`）；未通过的发布 tag 会被跳过，绝不使用。为测试而覆盖发布端点时，也不跳过任何检查。
- **不经过 shell。** 包管理器命令是由 `PackageManagerArgs` 根据固定的包名和校验过的版本构造的 argv 列表，不经 shell 运行。在 Windows 上，npm、pnpm 和 yarn 是由 cmd.exe 运行的 `.cmd` 垫片，给参数加引号并不能让 `&`、`|`、`<`、`>`、`^` 或 `%` 失效；正是先校验了版本，这次调用才安全。
- **不悄悄降级。** 目标版本比正在运行的版本旧时，需要 `--allow-downgrade`；`CheckUpdateTarget` 在一次调用中同时检查版本和降级。
- **如实的状态。** 只有进程内验证运行并通过时，`signature_status` 才是 `verified`；走包管理器的路径报告 `not_checked`，不存在签名时报告 `unavailable`。
- **Skill 来自已安装的包。** `update` 从已安装的包把 Skill 复制到已经安装了它们的 Skill 目录中，绝不从网络来源同步（SKL-009）；README 中的 Skill 安装器也以固定的版本运行（`npx skills@<version> …`，REPO-010）。
- **漂移检查。** 以副本方式引入的 aicli 文件（`internal/aicli/`、`<pkg>/_aicli/`）与其 `MANIFEST.json` 中的摘要不符（离线、严格），或者以副本方式引入的规范文件与固定的 tag 不一致（联网时），`scripts/check-spec.js` 就让 CI 失败。要修写入门控，就改模板，绝不改内置副本。

原因：2026-10 的工具群审计发现，有的 `update` 命令把未经校验的版本字符串传给 `npm.cmd`，在 Windows 上，这等于在一次不经写入门控的调用里执行任意命令：其中 2 个工具可以通过一个标志利用，另有 5 个工具可以通过精心构造的发布 tag 触达；只有 1 个工具校验了版本。4 个工具把显式指定的更旧版本当作「更新」接受。v1 自己就规定每次更新都从仓库拉取未固定版本的 Skill，所以谁控制了默认分支，谁就能不经发布改变 Agent 的指令。这些工具各自写了自己的更新路径；一个只需测试一次的内置命令取代了它们。

检查：aicli 的测试拒绝 `1.0.12&calc`、`1.2` 和 `1.2.3 || x`，接受 `1.2.3` 和 `v1.2.3-rc.1`，并覆盖签名无效、身份不符和校验和不符的情况；评审发布工作流、CI 审计和 `UpdateConfig`；漂移检查在合并和发布时都会运行（VER-008）。

## 检查清单

### SEC-060 按风险档的检查清单

评审时勾选工具所在风险档及以下各档的全部条目。每一项都注明了定义它的规则。

T0，所有工具：

- [ ] 风险档写在 `reference.risk_tier` 和 SECURITY.md 中，不低于声明的效果所要求的最低档，用一句话说明最坏情况（SEC-001）
- [ ] 外部文本列在 `meta.untrusted` 和每个 schema 的 `untrusted_fields` 中；Agent 据以行动的字段只由工具控制的值构造（SEC-002）
- [ ] 输出、预览、令牌、记录、日志或示例中没有机密（包括上游返回的机密），也没有机密的未加盐哈希（SEC-021）
- [ ] 工具只连接配置的上游，以及在 `update` 和 `doctor` 中连接它的发布源；没有遥测；其他任何目的地都列在 SECURITY.md 中（SEC-022）
- [ ] 存储的凭证遵循钥匙串模式；文档给出的通道是环境变量；配置文件和设置文件中都没有机密；`context.credentials.source` 如实（SEC-040）
- [ ] 校验和已签名，进程内验证，合并和发布时对每个分发生态做依赖审计，CI 从 tag 构建，安装时不下载（SEC-050）
- [ ] `update` 是依据 `App.Update` 提供的 aicli 内置命令，工具没有自己的更新代码：严格 semver，不经 shell 的 argv，`--allow-downgrade`，如实的 `signature_status`，Skill 从已安装的包复制（SEC-050）
- [ ] 以副本方式引入的 aicli 和规范文件通过漂移检查（SEC-050）

T1，还要：

- [ ] 每个非 `observe` 命令都以如实的效果注册，并经过 aicli 的写入门控；工具里没有令牌、密钥或存储相关的代码（SEC-020）
- [ ] 符合性测试套件在 CI 中运行，每个写命令都有样例；输入只以声明的参数、aicli 文件输入或身份的形式进入命令（SEC-020）
- [ ] 没有授权范围时拒绝写入；工具从不写授权范围文件；目标键是规范化的（SEC-010 至 SEC-012）
- [ ] SECURITY.md 给出授权范围文件的路径、怎样授予和撤销，以及如实的保护声明（SEC-011、SEC-013）
- [ ] 状态存储的权限和 `context.state.protection` 在每个支持的操作系统上都正确（SEC-030）

T2，还要：

- [ ] 不可逆和账户级的命令声明为危险，批量命令只在它做的事危险时才声明为危险；`deliver` 和 `configure` 保持危险（SEC-001）
- [ ] `deliver` 命令的预览列出其目的地，并强制执行 `destinations`（SEC-012）
- [ ] 凭证和配置档命令声明为 `configure`（SEC-040）
- [ ] Skill 在用户没有明确要求的危险操作之前停下（SKL-005）
